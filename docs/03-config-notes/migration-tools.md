## 一句话结论

> S/4 新实施优先用迁移驾驶舱（SAP S/4HANA Migration Cockpit，Fiori「迁移您的数据」应用，老事务 `LTMC` 在新版本被替代，入口随版本变化以你的系统为准）；ECC 存量项目 `LSMW` 仍可用。工具是小事，「模板 → 校验 → Staging → 转换 → 迁移 → 三核对」的闭环纪律才决定迁移质量。

## 症状

- 模板上传后校验错误成片刷屏：改一批冒一批，迁移动工三天数据还没进 Staging。
- 迁移后数量对、余额错：主数据条数与模板行数一致，`FBL3N` 科目余额却与模板合计差一截，试算平衡表对不平。
- 重复迁移导致主数据翻倍：客户 `100001`、供应商 `200001` 各出现两条，未清项重复挂账。

## 根因（按概率）

| 根因（按概率） | 验证动作 | 修复动作 |
|---|---|---|
| 模板字段错位/必填漏填（列序被挪、复制粘贴带空格） | 看驾驶舱校验报告的错误行号与字段提示 | 按报告逐行修模板重传，不绕过校验硬灌 |
| 公司代码层漏迁（只迁了全局层数据） | `FS00`/`XD03` 查公司代码 1000 层是否存在 | 先补迁公司代码层，再迁交易数据与余额 |
| 重复执行迁移包（前次失败未处理又整包重跑） | 迁移日志核对该对象的执行次数与状态 | 删重复主数据，失败包处理完标记完成再继续 |
| 未清项参考字段缺失（凭证号/凭证日期/到期日） | 抽查校验报告必填提示与 `FBL3N` 未清明细 | 模板补齐参考字段后重传该对象 |

## 配错会怎样

- 主数据翻倍后，付款、对账全出现「同名同号」二义性，清理成本远高于迁移本身。
- 余额不平直接卡死上线日历：T-3 余额导入签核过不了，后续切换步骤全部顺延（见[上线切换 Runbook](/02-project/go-live-runbook)）。
- 未清项缺参考字段：迁移「成功」但清账时匹配不上，账龄与催收口径失真。

## 怎么配置

1. 选迁移对象：科目、客户（如 `100001`）、供应商（如 `200001`）、资产、未清项、余额——按「主数据 → 交易数据 → 余额」顺序分批，先决条件没到位的对象不放进同一个包。
2. 下载模板 → 填数：模板列自带校验规则（必填、格式、值表），在 Excel 阶段就把错误用完，别留到上传后。
3. 上传 → Staging（暂存）→ 转换 → 迁移：每步看日志；迁移完成后逐对象核对迁移日志与对象清单。
4. ECC→S/4 升级项目还常用技术迁移（分批分阶段搬数据，属 Basis 范畴），FICO 顾问只负责迁移后的对账口径。
5. `LSMW`：老而稳，ECC 项目与老顾问习惯仍在用；支持录屏、标准批量对象、BAPI、IDoc 四种导入方式。S/4 新实施没有理由再新开 LSMW 工程。
6. 选型原则：S/4 新实施优先驾驶舱；ECC 存量项目 LSMW 仍可用；复杂未清项迁移（分年度分币种、参考字段要求高）无论选哪个工具都要试点先行——先迁 20 条走通全流程再放量。

```mermaid
flowchart LR
    A[下载模板] --> B[填数上传]
    B --> C[校验报告]
    C -->|错误清零| D[Staging]
    C -->|有错| B
    D --> E[转换]
    E --> F[迁移]
    F --> G[三核对]
```

## 怎么验证

迁移完成后逐对象核对，数量、余额、抽样三层缺一不可。

**验证 T-Code**：`LTMC`
**验证判据**：数量——科目/客户/供应商主数据条数 = 模板行数（去掉表头与错误行）；余额——`FBL3N` 各科目余额与模板合计一致、试算平衡表借贷相等；抽样——随机抽 20 条明细做字段级比对（名称、统驭科目、付款条件、未清项参考字段）。
**失败对照**：条数不符 → 回迁移日志查是否重复执行、有无整段错误行未重传；余额不符 → 先查公司代码层是否漏迁，再核对模板合计口径；字段错 → 修模板重传该对象，迁移后再抽 20 条复核。
